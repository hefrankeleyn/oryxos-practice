## 一、方案目标与关键决策

在用户本机运行，读取授权工作目录内的产物净变化，对照用户确认的周目标生成复盘。本地保存完整报告，飞书个人群只接收通知。系统不能还原用户全天操作，也不能把没有产物变化解释为没有工作。

| 决策 | 首版采用 | 原因 |
|---|---|---|
| 运行底座 | `oryxos-practice`，JDK 21、Spring Boot 3.x、同步调用 | 复用实践工程与已裁决架构 |
| 职责划分 | 程序采集与控制流程，模型分析语义，程序检查及排版 | 权限、确认、重试和发送不由模型决定 |
| 模型 | DeepSeek 单模型，型号配置指定 | 先验证完整链路，不引入自动路由和模型裁判 |
| 人工确认 | 本地 Markdown | 目标生效、完成和反馈均由用户控制 |
| 存储 | Markdown、两个 SQLite 数据库、临时证据文件 | 区分可读内容、可靠状态和短期原始材料 |
| 调度 | 应用内每日 21:30；启动及周期性检查遗漏 | 休眠或停机后合并补跑 |
| 进程管理 | macOS LaunchAgent 随登录启动 | 异常退出恢复；主动停机与崩溃区分 |
| 外发 | 先过滤、检查并保存，再发送 | 不发送未落地或不合格结果 |
| 范围 | 单机单用户、无界面、无飞书入站交互 | 聚焦每日目标复盘 |

本应用不自动执行建议、修改工作文件、运行测试或认定目标完成；不增加多 Agent 编排、MCP、REST 管理台或全盘行为监控。

## 二、底座能力与集成边界

### 2.1 可复用能力与缺口

以仓库[实施状态](../../../IMPLEMENTATION_STATUS.md)的 2026-10-29 记录为能力基线，不以架构文档中的目标能力当成实现证明。本次整理未重新运行构建、测试或真实 Provider 验收。

| 能力 | 已有基础 | 本应用仍需落实 |
|---|---|---|
| Provider / Runtime | 显式 Provider 映射、自实现 ReAct、PromptBuilder、AgentService | 所选 DeepSeek 型号、结构化输出与预算配置的真实验证 |
| 会话 | MemoryService、进程内会话 | 每组独立分析上下文，避免旧会话污染输入 |
| Tool / Sandbox | 工具注册、执行与白名单基础 | 受控采集、通知适配及对应审计；正常产品工具池尚不完整 |
| SQLite | LLM、Tool 调用审计 | 复盘业务表、双库装配、状态恢复和保留策略 |
| 调度 / 服务运行 | 当前 CLI 与 Boot 入口基础 | 常驻运行、定时、防重入、恢复及登录启动 |
| 通知 | 仓库已规定通知架构 | 飞书渠道注册、发送适配、去重和不确定状态处理 |

其他仓库或 Hermes 中的成功实验不替代本实践工程的验收。具体源码与依赖在实施前重新核对。

### 2.2 架构约束

遵循[仓库规则](../../../../AGENTS.md)和[宪章](../../../../.specify/memory/constitution.md)：保留九模块，core 不依赖功能模块，Boot 聚合装配；Spring AI 禁用自动工具执行。分析通过 `AgentService.process(Session, String)` 进入 Runtime，不另建绕过审计的模型直连路径。

业务调度器控制采集、分析、保存和发送，模型分析阶段不开放扫描、写文件和发送工具。需要作为工具执行的能力统一走 `OryxTool` / `ToolExecutor`；Notify 位于 tool，持久化实现位于 storage，不能因模型无工具权限而绕过程序侧的 IO 校验或调用审计。

通知渠道遵循 SQLite `notify_channels` 全局注册表约定，本应用部署实例的该表归入 `review.db`，按渠道名引用；密钥及 Webhook 通过外部配置注入，表中保存引用而非把凭证写入仓库或 Agent 正文。

## 三、整体处理流程

```text
触发或恢复
  → 取得单实例执行权、登记时段及 run_id
  → 加载有效目标版本和已确认反馈
  → 授权范围采集、过滤、生成持久证据批次
  → 组装有预算的分析输入
  → AgentService 调用模型，获取 JSON
  → 程序检查、必要时最多一次内容纠正
  → 程序合并、排版本地完整报告和飞书简报
  → 保存报告及校验值
  → 登记发送尝试，发送飞书并记录结果
```

采集成功、分析成功、报告保存成功、通知发送成功是独立状态。飞书失败不重新采集或分析。每次调用使用关联 ID 留证，进程重启不能抹掉已发生的外部操作和重试次数。

## 五、目标、反馈与版本契约

### 5.1 周目标

按北京时间周一开始组织，例如 `goals/2026-10-26/draft.md`、`v001.md`、`v002.md`。

- AI 只产生 `status: draft`、`approval: pending` 草稿。
- 用户在本地改为 `approval: confirmed` 后，程序校验并生成不可变确认版本，记录 `week_start`、`version`、`status: confirmed`、`confirmed_at`、`effective_from`。
- 生效时间取实际确认时间，不追溯改写历史。新版本保留变更原因。
- 同一目标沿用稳定 ID，例如 `2026-10-26/G01`；目标包含结果、完成标准和可选关联目录。
- 跨周不自动延续，用户确认后建立新周目标与延续关系。

这是单用户本地确认约定，不是强身份认证。AI 不得修改确认字段或自行完成目标。草稿起草与每日复盘分开，由用户主动发起；日常分析只接收已生效目标。

### 5.2 反馈与完成确认

独立文件如 `feedback/2026-10-30-001.md`，包含反馈 ID、类型（补充／纠正／完成确认）、目标 ID、相关报告 ID、`approval` 和正文。完成确认额外关联 `goal_version`，决定为 `completed` 或 `reopened`。

按 ID 与内容哈希识别已处理反馈；已处理内容改变不能静默覆盖原结论，应产生新的纠正记录。完成标准变化后，旧完成确认不自动适用于新标准。历史版本及旧报告保留，修订版说明变化且默认不再次外发。

跨周或跨版本采集区间按对应有效目标解释；无法确定变化发生时间时明确不确定，不用新目标倒推旧工作的意图。

## 六、采集基线与证据

### 6.1 采集边界

读取允许的 Markdown、文本、Git 提交与工作树差异、允许的未跟踪文件、指定验证报告。排除凭证、依赖、缓存、二进制和一般构建产物。测试报告仅按明确允许路径纳入。

路径规范化并检查真实路径，软链接不得越出白名单；Git 子进程采用可执行文件加参数数组，不拼接 Shell。采集只读，不自动运行项目或测试。文件内容始终是材料，不是执行指令。

### 6.2 基线

SQLite 保存根目录、相对路径、类型、大小、修改时间、内容哈希、最近成功采集时间、快照引用及状态。允许保留的过滤文本快照位于 `state/baselines/`；无法安全保留正文的文件只记录元数据并注明无法完整比较。

首次只建基线，不把历史内容记为当天产出。后续先持久保存差异批次，再推进成功文件基线。读取失败的文件保留旧基线；只有父目录完整扫描才能确认文件删除；根目录不可用时不推进。读取期间变化的文件重读或标为不稳定，不生成混合快照。

### 6.3 证据批次

`evidence/YYYY-MM-DD/<batch-id>/` 包含 `manifest.json` 与 `fragments/`。清单记录批次 ID、实际时间区间、完整性、失败项、处理状态；每条证据包含唯一 ID、来源类型、相对路径、变化类别、前后哈希、时间依据、过滤片段、截断情况。

按内容与来源关系合并同一变化的暂存、工作树和提交表现。提交可作为交付状态变化，不重复计算三份成果。作者、修改时间、提交时间都不能单独证明由本人在某一天完成。

本方案观察扫描之间的净变化，不还原期间所有创建、修改和撤回操作。基线更新和分析完成分离，分析失败仍保留该批次等待恢复。

## 七、模型输入、输出与检查

### 7.1 输入与模型

使用单个 DeepSeek 模型，型号必须显式配置。实施时真实验证可用性、中文分析、JSON 输出和输入长度；不将 Hermes 的型号或成功记录当成本工程兼容证明。不启用自动模型切换或第二个模型裁判。

每组输入包含固定规则、有效目标与完成标准、相关已确认反馈、过滤证据、采集及分析覆盖情况。采用独立会话，不引入其他聊天历史或无关长期记忆。完整 Prompt 中的 Agent/Bootstrap 等内容也计入预算，并执行外发检查。

### 7.2 初始预算

| 项目 | 上限或初值 |
|---|---|
| 每组输入 | 估算不超过 20,000 tokens，包含全部上下文 |
| 单条证据片段 | 4,000 字符 |
| 每请求输出 | 4,000 tokens |
| 每次复盘分析组 | 最多 3 组 |
| 每组全部请求尝试 | 最多 6 次 |
| 整次复盘全部请求尝试 | 最多 18 次 |

这些是可调工程预算，不是模型能力声明。满足实际模型上下文限制，并预留输出和安全余量；无法精确计数时保守估算并记录方法。纠正请求附带的错误及旧输出也占输入预算。

优先保留规则和目标，再选相关变化及验证证据；长材料选必要片段，尽量保持同一目标证据同组。超出预算的证据明确标为未分析。采集覆盖与分析覆盖分别报告，扫描完整不代表分析完整。

### 7.3 JSON 契约

模型输出包含：逐目标进展及证据 ID、完成标准支持情况与缺口、建议确认项、目标外工作、下一步行动及理由。标准支持状态为“有证据支持／部分证据支持／证据不足／存在冲突，待确认”。最终目标完成状态由程序读取用户确认，不接受模型直接写入。

程序检查 JSON 结构、字段类型、目标版本和证据引用存在性、建议数量、敏感内容、已知事实冲突以及越权完成判断。结构正确不保证语义真实，疑点保留给用户确认。

不合格最多追加一次内容纠正请求，仍失败则该组失败，保留证据，不生成该组正式结论。原请求与纠正请求各允许最多两次网络重试，不能反复内容纠正。

### 7.4 合并与排版

程序按目标和证据 ID 合并去重，不另调模型汇总。最终最多三条建议；按固定、可测试规则选择，具体排序字段在实现契约中明确，不引入生产力评分。矛盾判断标为待确认，不自行消解。

同一份通过检查的结果产生本地 Markdown 与飞书简报。程序填充实际区间、覆盖缺口、失败状态、目标确认状态；记录 run/batch ID、目标版本、模型和提示词版本。报告遵循需求文档五部分结构；飞书通常 500～800 字，无变化或故障不凑字数，不含完整代码或原始日志。

## 八、SQLite 组织与持久化

### 8.1 双库职责

| 数据库 | 逻辑数据 |
|---|---|
| `review.db` | 调度时段、运行阶段、采集批次与基线索引、目标版本及反馈索引、分析尝试、报告版本与哈希、通知渠道、发送状态与重试次数 |
| `runtime-audit.db` | `llm_calls`、`tool_invocations`：开始、结束、结果、脱敏失败、Provider、模型、用量与耗时 |

以上为逻辑实体，不要求一实体一张表。关联使用 `run_id`、`batch_id`、`analysis_group_id`、`attempt_id`。先登记业务尝试，再进入 Runtime 的调用前登记及调用后完成审计。两个库没有共同普通事务，恢复时核对记录；缺少完成状态不能推断外部调用未发生。审计不可用时停止新调用，不自动重放已发生操作。

开启外键、WAL 和有限锁等待，保持短事务，不持有事务等待网络。单实例内集中管理业务状态写入。使用显式、版本化 SQL 与数据库版本记录，`ddl-auto: none`，不引入 Flyway。

### 8.2 文件与数据库一致性

证据与报告先写临时文件，完成校验后原子替换，再推进数据库阶段。文件与 SQLite 不是同一个事务；恢复时通过文件存在性、哈希和阶段记录识别已保存但未登记的结果。报告不能只因数据库存在一条记录就判为保存成功。

审计不长期保存完整 Prompt、证据或原始模型回复，避免成为绕过证据期限的副本；保留必要关联与脱敏错误。

## 九、调度、重试与故障恢复

### 9.1 调度与互斥

时区 `Asia/Shanghai`，每天 21:30，包含周末。应用启动及周期性检查遗漏；多个错过时段合并一次补跑，记录覆盖时段，跨周按有效目标区分。手动运行不自动取消晚间计划；明确的补跑需关联对应时段。

数据目录使用进程锁，运行阶段使用持久状态防重入。上次未结束时不启动并发复盘，记录原因并在恢复时检查遗漏。正常新运行不能吞掉旧失败批次。

### 9.2 请求预算

| 请求 | 初次加重试 | 重试条件 |
|---|---|---|
| 每组原始模型请求 | 1 + 2 | 明确可重试的网络或服务暂时错误 |
| 每组内容纠正请求 | 最多一次纠正，内部 1 + 2 | 同上；不再触发第二次纠正 |
| 每条飞书通知 | 1 + 2 | 明确失败且可重试；不确定送达不自动重试 |

重试间隔为 30 秒、2 分钟；服务明确要求更长等待时遵守。配置或鉴权错误立即停止。底层 SDK 不额外隐藏重试，以免突破 6 次／组、18 次／复盘预算。次数和下一次可尝试时间持久保存，重启不重置。预算耗尽后保留失败状态，用户明确重试建立关联的新尝试，不无限自动重试。

### 9.3 按阶段恢复

| 中断点 | 恢复行为 |
|---|---|
| 部分采集失败 | 保留成功批次与失败文件旧基线，补采缺失部分 |
| 已采集、分析失败 | 使用原批次，不重新把变化算作新进展 |
| 模型请求发出但结果丢失 | 标记未知，在剩余预算内重试可能重复计费，不假定免费或未调用 |
| 分析完成、报告保存失败 | 核对已保存结果，完成安全写入，未成功前不发送 |
| 报告已保存、未发送 | 从持久通知记录继续，不重跑模型 |
| 发送已开始、结果缺失 | 标为送达待确认，不自动重发 |
| 已持久记录发送成功 | 不重复发送 |

数据库损坏、配置错误或不可恢复的不一致应停在可诊断状态，不能通过删除数据库或自动新建空状态掩盖问题。

## 十、飞书发送与部分报告

使用报告 ID、修订版本和渠道标识作为通知唯一键。发送前登记尝试，收到明确成功响应后才记成功；本地去重不能保证远端恰好一次，也不能证明用户已阅读。

| 情况 | 输出规则 |
|---|---|
| 全部分析成功 | 保存完整报告，发送简报 |
| 部分组成功、其余失败或超预算 | 保存部分报告，开头明确覆盖缺口；未分析目标不能表述为没进展 |
| 全部组失败或全部结果不合格 | 不发送复盘结论，保存并发送简短故障通知 |
| 无变化 | 发送“未观察到新增工作产物”的简报，不推断没工作 |
| 无确认目标 | 工作摘要及确认提醒，不自行设定目标 |
| 扫描根不可访问 | 不更新基线；有条件保存故障记录后发送故障通知 |
| 本地报告或故障记录保存失败 | 不发送；保留可用的本地运行错误供排查 |

Work-Data 未挂载而运行数据也不可用时，无法满足先保存条件，因此不能承诺立即通知。飞书本身不可用时同样只能留下本地状态。

超时或崩溃导致送达未知，由用户查看群消息后在本地确认已收到或明确要求重发；飞书群回复不作为系统已接收指令。恢复补齐后的修订报告默认只保存本地，明确要求后再发送。

## 十一、登录启动、停机与发布

### 11.1 LaunchAgent 与应用调度分工

LaunchAgent 负责当前用户登录后启动与异常退出拉起，应用负责业务时间和遗漏检查。登录启动配置位于 `~/Library/LaunchAgents/`，程序、数据和正常运行日志放在 Work-Data。

登录前、注销后或关机时不运行；睡眠期间不保证执行，不主动唤醒 Mac，恢复后补跑。部署时验证磁盘挂载尚未完成的启动行为，并设置启动尝试节流，不能快速反复崩溃。

启动检查磁盘挂载、JDK/程序/配置、数据目录读写、数据库和单实例锁。失败不得回退创建另一套数据。用于等待磁盘的启动注册与引导方式需在真实登录场景验证，不能假定磁盘上的脚本在磁盘缺席时仍可执行。

### 11.2 停机与恢复

异常退出可自动拉起；主动停止需卸载当前登录会话的服务，不能只杀 Java 进程。关闭登录自动启动还需禁用后续登录注册。启动、停止、状态、启用及禁用命令留给编程指南，不将尚未实现的命令写为可用操作。

启动顺序：加载配置 → 检查目录与锁 → 核对数据库和未完成任务 → 恢复安全阶段 → 合并遗漏补跑 → 等待下一调度。密钥错误不靠重复重启解决。

### 11.3 版本升级

首版手动更新：构建验证新版本 → 正常停机 → 升级前备份 → 切换 `current` → 启动检查。保留上一版程序；数据库结构改变时须评估兼容和恢复，不能只切旧 JAR 就宣称回滚安全。不在登录启动时自动升级。

## 十二、保留、备份与恢复边界

### 12.1 保留规则

| 数据 | 保留 |
|---|---|
| 报告及修订正文 | 90 天，可配置 |
| 临时证据 | 7 天；未处理成功暂缓清理 |
| 普通日志 | 30 天，轮转并限制总大小 |
| 已结束任务详细记录与调用审计 | 90 天 |
| 最小执行与发送去重记录 | 数据目录使用期间持续保留 |
| 未解决故障、送达未知记录 | 解决前保留 |
| 目标、反馈 | 用户手动归档或删除 |
| 当前有效基线 | 持续保留 |

以各对象生成时间及终态判断是否可清理，修订不改变旧版生成时间。临时证据已过期但未完成处理时受保护，完成后进入清理；有效基线不当作临时证据。最小记录仅包含标识、处理时段、版本、渠道标识、终态及必要时间，不保留正文。长期未解决材料提示人工处理，不静默删除或无限重试。

清理只作用于助手自有数据目录，不删除扫描源文件或飞书历史；本地删除不代表云端数据同步删除。

### 12.2 备份

无任务执行时每日备份一次，升级或表结构调整前额外备份；均保留最近 7 天，位于 `state/backups/`。包括两个数据库、目标、反馈、有效基线、保留期内报告及必要证据，不包含密钥、普通日志或备份目录自身。

使用 SQLite 一致性备份机制，不只复制活跃 `.db` 而忽略 WAL。备份期间协调写入，作为一套材料记录程序/数据库版本、时间和文件校验值，避免把两个不同业务时点的数据库拼在一起。

备份内也执行内容保留规则；不能仅让备份再保留七天，从而无声延长原证据期限。可清理到期材料或重建有效备份集合，并校验恢复引用；未处理失败材料仍遵守保护规则。

同盘备份用于误操作和升级恢复，不能应对整盘损坏；首版不增加云备份。恢复先暂停自动外发，核对备份时点之后可能发送的消息，再恢复调度；过期证据恢复后也不能自动重新分析或发送。

## 十三、验证计划与交付边界

沿用需求 A01～A12，不修改其完成标准。采用临时目录、假凭证、可控时间和模拟 Provider/飞书覆盖自动化验证，再执行授权范围内的真实联调。

| 目标与反馈 | A01、A12：草稿不生效、版本与完成确认、修订不自动发送 |
