# 基于工作产物的每日目标复盘助手：业界调研

> 调研日期：2026-10-30。本文依据已审阅的首轮调研结果整理。
> 资料范围：官方产品介绍、帮助文档和隐私说明；未逐一安装实测。产品能力可能随版本变化。
> 状态：调研文档。候选定位与待验证假设不等于已确认需求、已实现功能或已证明的市场空白。

[toc]

## 一、研究对象与核心问题

本项目源于一个个人工作场景：每天定时扫描指定工作目录，根据当天的工作产物变化，结合个人目标形成进展复盘和下一步建议，并将报告发送到飞书。

工作目录只能提供部分工作证据，无法代表用户的全部行为。会议、阅读、思考及浏览器中的操作可能没有留下文件；文件修改也可能来自自动保存、构建、同步或 AI 批量生成。因此，需要区分观察事实、分析推断和用户确认，不能将“没有发现产物”解释为“没有工作”。

本次调研回答五个问题：

1. 哪些现有方案可以记录工作活动或收集工作产物？
2. 哪些方案已经能自动总结、关联目标并提供复盘？
3. 哪些自动化基础可以承担定时执行和报告投递？
4. 我们的场景是否还存在值得验证的价值？
5. 应先验证哪些假设，再确定需求和技术方案？

## 二、调研方法与比较边界

按能力选择样本，而不是仅比较名称中包含 Agent 的产品：

- 活动记录：ActivityWatch、RescueTime。
- 工作上下文采集：screenpipe。
- 开发活动日报：Gitmore。
- 目标规划与复盘：Sunsama。
- Agent 自动化：Hermes Agent。

比较维度为数据来源、目标关联、报告与投递、隐私边界，以及与本项目的适配距离。本次样本并非完整市场清单，没有进行性能、安全、成本或长期使用效果的实测比较。

本文使用三种表述：

- **资料确认的事实**：官方资料明确描述的能力，附来源。
- **分析判断**：结合本项目场景作出的解释，不当作产品官方结论。
- **待验证假设**：需要后续实验或用户反馈支持的判断。

“本次未确认支持”只表示证据不足，不表示产品不存在该能力。

## 三、现有方案分析

### 3.1 ActivityWatch：自动活动记录与可选 AI 总结

**资料确认的事实：** ActivityWatch 自动记录应用和网站使用情况，采用本地存储；其隐私说明还描述了可选 AI Summary。启用该功能并主动生成摘要时，会将限定的活动汇总发送给所选第三方模型服务。不能将本地存储理解为所有使用方式都不向外发送数据。[来源 S1、S2](#参考来源)

**分析判断：** 值得借鉴自动采集、分类汇总及用户对数据的控制。本项目关注文件和代码的内容变化；本次资料未确认 ActivityWatch 直接以这些差异判断个人成果目标的进展。

### 3.2 RescueTime：时间目标与行为反馈

**资料确认的事实：** RescueTime 提供活动时间记录及报告，支持为活动类别、应用或项目设置时间目标，并在达到阈值等条件下触发提醒或动作。[来源 S3、S4](#参考来源)

**分析判断：** 它说明自动记录与目标反馈已有成熟产品形态，但时间投入和成果完成需要分别评价。“专注三小时”不能直接证明“完成一份需求文档”。

### 3.3 screenpipe：更广的工作上下文

**资料确认的事实：** screenpipe 可采集屏幕文本等上下文，提供本地搜索 API；连接资料还列出了笔记、任务及协作系统等来源。官方说明指出，使用云端 AI、转录或远程工作流等功能时，数据可能离开本机。[来源 S5、S6](#参考来源)

**分析判断：** 它能为文件系统之外的工作提供补充线索，但采集范围扩大也增加权限、过滤和处理负担。首版是否需要屏幕采集应单独验证，不应直接列为前置条件。

### 3.4 Gitmore：从代码协作记录生成日报

**资料确认的事实：** Gitmore 汇总提交和 PR 等 Git 活动，生成每日、每周或自定义周期的报告，并发送到 Slack 或邮件。[来源 S7](#参考来源)

**分析判断：** 它与“从产物生成报告”的需求直接相关，可借鉴活动聚合方式。本次未确认其覆盖未提交的本地变化、非 Git 笔记及用户自定义的本地目标文件；这些需进一步核实，不能据此断言不存在。

### 3.5 Sunsama：任务与目标之间的关联

**资料确认的事实：** Sunsama 支持周目标与任务关联、周复盘；其 AI 助手可利用任务、日历、目标等信息辅助规划并总结已完成工作。[来源 S8、S9、S10](#参考来源)

**分析判断：** 这是目标复盘的重要参考，说明“AI 总结加目标规划”并非新的能力组合。本项目需要验证的是：直接使用已有本地产物，能否减少用户维护任务和汇报的负担。本次资料未确认其提供本地工作目录增量扫描。

### 3.6 Hermes Agent：可配置的定时分析与投递

**资料确认的事实：** Hermes 支持定时任务、关联 Skills、保存输出，并提供飞书等投递目标。官方定时任务说明还区分执行与投递结果，包括投递失败或证据不足的情况。[来源 S11](#参考来源)

**分析判断：** 通用 Agent 已能承担定时分析与发送报告的基础流程。本项目仍需设计证据采集、目标判断和报告规则，但应先评估配置加少量工具是否已经足够，无需预设必须开发完整新平台。

## 四、横向比较与关键发现

| 方案 | 主要证据来源 | 值得借鉴的能力 | 本项目还需核实或补充的部分 |
|---|---|---|---|
| ActivityWatch | 应用、网站活动与时间 | 本地采集、分类、可选 AI 汇总 | 文件内容变化与成果目标关联 |
| RescueTime | 活动时间及项目工时 | 时间目标、报告与提醒 | 成果型验收判断 |
| screenpipe | 屏幕上下文及连接系统 | 查询工作历史、补充上下文 | 采集必要性、权限与噪声控制 |
| Gitmore | 提交、PR 等开发活动 | 自动聚合与定时报告 | 本地未提交变化、非 Git 产物与个人目标 |
| Sunsama | 任务、日历、目标 | 任务目标关联、规划与复盘 | 本地产物自动采集及其准确性 |
| Hermes Agent | 任务可访问的工具与上下文 | 定时执行、Skills、渠道投递 | 本场景专用采集和判断规则 |

### 4.1 活动、投入与成果需要分开

活动记录回答“观察到什么”，时间目标回答“投入了多少”，成果目标回答“是否达到完成标准”。报告应围绕用户明确的目标组织证据，不能用文件数、提交数或在线时长直接评价工作价值。

### 4.2 自动日报不是独有能力

现有方案已经覆盖采集、总结、目标规划和通知的多个环节。我们的候选价值是降低本地产物整理负担，并使目标进展判断可追溯；本次调研不足以证明商业需求或市场独特性。

### 4.3 报告生成与送达应分别判断

分析成功不等于飞书收到报告。可借鉴 Hermes 对执行与投递结果的区分，避免通知失败后不必要地重新分析，或重复发送。具体重试和去重机制属于后续技术方案。

## 五、候选定位与差异假设

### 5.1 候选定位

面向以本地文档和代码为主要工作产物的个人开发者，基于授权目录的变化和用户明确的目标，生成带证据、可纠正的每日进展复盘与下一步建议，并通过飞书送达。

这是调研形成的候选定位，具体需求范围将在下一份文档中确认。

### 5.2 候选差异

| 候选差异 | 含义 |
|---|---|
| 以工作产物为主要证据 | 关注文档、笔记与代码变化，包括选定目录中的未提交内容 |
| 以明确目标为判断依据 | 目标、优先级和完成标准由用户提供 |
| 判断可以追溯 | 引用路径、差异摘要或提交，不只输出笼统评价 |
| 区分完成程度 | 分别描述草稿、评审、实现、测试和上线状态 |
| 允许用户纠正 | 保留证据不足状态，允许补充会议、阅读和思考 |
| 建议具体且有限 | 根据目标差距提出下一步，并解释依据 |

例如，观察到规格、方案与 66 项未勾选任务，可以支持“完成任务拆解”的判断，不能推出“功能实现完成”。这类状态区分是待验证的报告质量要求。

## 六、替代方案与 OryxOS 的角色

| 替代方案 | 对照验证目的 |
|---|---|
| 手动将当天产物摘要与目标交给 AI | 判断自动采集能节省多少整理时间 |
| 使用通用 Agent 配置定时复盘 | 判断工具加提示词是否已经足够 |
| 使用现成目标与复盘产品 | 判断维护任务的成本与目标关联收益 |

选择 OryxOS 的当前理由，是利用熟悉的运行环境，实践适合个人目录、目标和飞书习惯的流程。尚无证据证明必须新增一套平台，或其他产品无法满足需求。

后续需核对所选 OryxOS 版本的真实能力，形成“可复用、需配置、需新增、待验证”清单。本次未重新审计官方仓库的实现状态，也不将实践仓库中的规划产物视为已经实现的能力。

## 七、待验证假设与验证方向

| 编号 | 待验证假设 | 建议验证方式 |
|---|---|---|
| H1 | 指定目录的产物能覆盖用户关心的大部分目标进展 | 用连续几天真实记录与用户补充对照，记录遗漏及原因 |
| H2 | 自动采集能减少复盘整理负担 | 对比手动复盘与自动复盘的准备、阅读和纠错时间 |
| H3 | 明确目标和验收标准能改善进展判断 | 逐条核对报告结论与原始证据，记录误判和证据不足项 |
| H4 | 基于证据的建议对用户有实际帮助 | 记录建议是否被采纳，以及未采纳原因 |
| H5 | 限定采集及外发范围后仍能形成有用报告 | 检查过滤后的证据是否足够，同时审阅模型输入和通知输出 |
| H6 | 定时投递比手动查看更容易形成复盘习惯 | 观察用户是否实际阅读、补充或纠正报告，而不只统计发送成功 |
| H7 | OryxOS 配置与少量工具能支撑首版 | 核对选定版本能力并进行隔离原型验证，避免提前扩大平台开发范围 |

这些验证尚未执行，不预设通过比例或成功结论。量化验收标准将在需求确认时制定。

## 八、后续需求与技术方案需要处理的问题

1. **变化识别：** 不能只依赖修改时间；需考虑扫描基线、内容差异、重命名及重复统计。
2. **噪声与归因：** 构建、同步和 AI 自动生成内容不直接等同于用户有效进展。
3. **完成判断：** 产物存在不等于通过验收，需表达待确认和证据不足。
4. **运行条件：** 电脑休眠、目录不可访问或 Work-Data 未挂载时，应报告采集失败，不能声称没有工作。
5. **数据边界：** 分别明确可读取内容、可发送给模型的片段以及可发送到飞书的报告信息。
6. **材料与指令：** 扫描到的文件属于分析材料，不能被当作执行动作的授权。

## 九、调研结论与下一步

已有产品充分证明了活动记录、自动总结、目标规划及定时通知存在可复用方案。本项目值得验证的方向，是将本地工作产物与明确目标连接起来，形成可追溯、可纠正的复盘，而不是假设扫描目录即可了解用户全部行为。

下一步应确认使用者、目标类型、授权目录、报告结构和首版边界，再编写需求分析。随后用连续几天真实产物与手动复盘对照，验证是否减少整理负担、降低误判并产生有用建议。
