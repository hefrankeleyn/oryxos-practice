# 每日目标复盘助手 AI 编程指南

[toc]

## 一、怎样使用这份指南

先用 Spec Kit 为整个助手建立一份独立规格，再按阶段实施。第一个里程碑是手动生成本地报告。开发时把每段提示单独发给项目对话，收到产物后再进入下一段。下文列的是预期证据，实际执行时填写测试结果。

产品行为与 A01～A12 以[需求分析](./02-需求分析.md)为准。模块边界、预算、数据保留与恢复规则见[技术方案](./03-技术方案.md)。七天试用要检验的价值假设见[业界调研](./01-业界调研.md)。

## 二、先把需求转成可审阅的任务

以下提示在 oryxos-practice 仓库的 Codex 对话中逐条使用。

| 步骤 | 给 AI 的提示 | 你审阅什么 |
|---|---|---|
| Specify | `$speckit-specify` 请读取 docs/homework/02/每日目标复盘助手/02-需求分析.md，为每日目标复盘助手建立独立规格。将首版行为写成可以独立验证的用户故事，保留 A01～A12 原意。报告新功能目录、检查清单和待澄清项后停止。 | 核对当前功能指针。用自己的话读每个故事，特别看谁能确认目标、哪些资料能外发。 |
| Clarify | `$speckit-clarify` 请核对前三份文档，只提出仍会改变可观察行为、范围或验收方式的疑问。将我的决定写回当前规格。 | 你决定产品取舍。已有明确答案的条目引用原文即可。 |
| Plan | `$speckit-plan` 请按 03-技术方案.md、现有宪章及当前源码规划。逐项区分已有能力和新增适配，给出数据契约、故障恢复及验证步骤。 | 查看一批证据从采集到外发的路径，核对权限、预算、审计、保存顺序及送达未知时的行为。 |
| Tasks | `$speckit-tasks` 请按下表阶段 0～6 标明任务归属、实际文件、前置依赖、关联验收编号和验证方式，单列真实联调与试用任务。 | 从 A01～A12 反查任务。检查首次本地报告能在启用通知和调度之前演示。 |
| Analyze | `$speckit-analyze` 请只读检查规格、方案、任务和宪章，列出漏项、冲突、错误依赖及位置。 | 影响用户行为的分歧由你裁决。修订后重新分析，通过后再实施。 |

## 三、逐阶段给 AI 下任务

每次都用下面一句开头，将方括号换成审阅后的实际任务编号，再接表中对应提示。任务尚未生成时保留占位符。

> $speckit-implement 仅执行当前复盘助手规格中 [任务编号范围]。先确认当前功能目录、前置任务和已有改动。完成后列出改动文件、验证命令、实际输出、对应验收编号及待验项，在本阶段停止。仅将具备相应证据的任务勾选为完成。

| 阶段 | 接在提示后面的任务内容 | AI 应交付的证据 | 你审阅什么 |
|---|---|---|---|
| 0．公共基础 | 在临时数据目录装配配置、双 SQLite 库、运行标识和调用审计。使用可控服务验证有效配置、配置错误和审计不可用三条路径。 | 临时目录结构、两库关联记录、脱敏错误和审计失败时外部调用计数为零的测试结果。 | 核对实际读写边界、配置中的模型和渠道引用。 |
| 1．目标与反馈 | 用一周目标演示 AI 起草、用户确认、周中修改、完成确认与反馈去重。 | 同一目标的草稿和两版确认文件、各自生效时间，以及重复读取反馈后的结果。对应 A01、A12。 | 亲自读一次新旧版本，确认可以辨认哪版生效、谁确认完成。 |
| 2．采集与证据 | 在临时工作目录建基线，再修改笔记、暂存并提交同一变化，加入假凭证和一个不可读项。核对采集清单及补采结果。 | 前后两次清单、相同变化的引用关系、过滤结果、失败项保留旧基线的记录。对应 A02～A04、A09。 | 对照亲手制造的变化，检查误收、漏收以及拟交给模型的脱敏片段。 |
| 3．手动生成本地报告 | 从手动入口加载已确认目标和证据，生成 JSON，检查后排版保存。覆盖无目标、无变化、超预算、模型纠正失败和本地保存失败。先用可控响应，再单列真实 DeepSeek 联调。 | 本地报告样例、目标版本、证据清单、JSON 检查结果、重试次数和输出路径。覆盖 A04～A07、A10、A12 中的本地行为。 | **第一次完整审阅报告。**核对每条判断的证据、未满足的标准、覆盖缺口和下一步建议。 |
| 4．飞书通知 | 从已保存报告生成个人群简报。模拟明确失败、超时未知和重启，核对去重与修订版发送规则，再进行约定的真实收件验证。 | 同一报告的发送记录、重试次数、超时后零自动重发、保存失败时零发送，以及群内实际收到的脱敏样例。对应 A04、A07、A10～A12。 | 首次真实发送前看简报和目的群。发送后核对群消息与本地报告是否对应。 |
| 5．调度与恢复 | 用可控时钟模拟北京时间周末 21:30、多个遗漏时段、并发触发与跨周补跑。在采集后、报告保存后、发送开始后分别中断并恢复。 | 调度时段到运行 ID 的映射、一次合并补跑的实际区间、各中断点恢复前后的状态和外部调用次数。对应 A07～A11。 | 核对跨天报告能说明覆盖时间，跨周采用当时有效目标，送达未知交由人工处理。 |
| 6．部署与维护 | 先在隔离目录演练登录启动、主动停止、异常拉起、延迟挂载、升级与备份恢复。用可控时间核对清理期限，再按审阅结果部署和试用。 | 实际启停命令及状态、故障恢复记录、7/30/90 天边界与未处理证据保护结果、恢复旧备份后暂停外发的记录。 | 启用常驻进程前核对程序、数据、日志和凭证位置。连续七天记录遗漏、误判、阅读纠错耗时及建议是否有用。 |

## 四、首次本地报告怎样验收

在临时目录中确认一个周目标，例如“形成一次可复现的 Hermes Memory 实验记录”，并约定完成标准包含新会话验证。首次运行建立基线。随后只新增一份实验步骤笔记，写明尚待新会话验证，再手动生成报告。

你应该能从报告中找到对应的目标版本和笔记变化，看到“实验步骤已整理”及“缺少新会话验证结果”。如果报告声称跨会话验证已通过，就沿证据 ID 回查清单、模型输入和 JSON，定位是哪一步把计划误读成了结果。再通过本地 Markdown 补充一条确认反馈，核对修订版如何说明变化以及旧报告是否仍可查阅。

使用模拟响应时记录程序检查和排版结果。实际调用 DeepSeek 后另记模型名称、脱敏调用记录和真实报告，由你判断语义是否准确。七天试用再回答这个助手是否减少复盘负担。

## 五、每轮怎样收尾

阶段交接保留一行可追溯记录，例如“任务编号｜验收编号｜输入样例｜预期｜实际｜证据位置｜待处理差异”。程序测试、真实模型响应、飞书收件和个人试用分别记录。若发现某项需扩大扫描范围、改变外发内容或调整完成标准，先列出受影响的需求和验收项，交由用户审阅，再同步规格、方案与任务。
