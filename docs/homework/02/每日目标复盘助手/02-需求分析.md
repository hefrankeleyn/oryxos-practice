# 基于工作产物的每日目标复盘助手：需求分析

> 确认日期：2026-10-30。
> 状态：根据用户逐项确认形成的首版需求基线，尚不代表功能已经实现或验收通过。
> 前置文档：[01-业界调研](./01-业界调研.md)。本文明确用户行为、范围和完成标准；接口、存储结构及实现方式留给技术方案。

[toc]

## 一、项目目标与使用者

首版仅服务用户本人，覆盖 AI 学习和项目开发。核心问题是：**每天做的事情有没有推进本周目标？** 同时减少工作回顾的整理负担，并提供下一步建议。

系统基于指定目录中的工作产物变化，将证据关联到用户确认的周目标，形成每日复盘，在本地保存完整报告，并向只有用户自己的飞书群发送简报。

系统只能观察部分工作证据，不能知道用户全部行为。会议、阅读和思考等可由用户主动补充；没有发现产物变化不能被解释为没有工作。

## 二、核心概念与判断边界

| 概念 | 定义及边界 |
|---|---|
| 周目标 | 用户提供想法，AI 起草，经用户确认后生效的本周预期结果 |
| 完成标准 | 判断目标完成所需的结果与证据；不能只以文件存在或数量判断 |
| 工作产物 | 允许范围内的文档、笔记、代码变化和验证记录 |
| 证据 | 可追溯的产物变化、验证输出或用户主动确认；需注明来源 |
| 进展判断 | AI 根据证据对目标推进情况作出的建议性判断 |
| 目标完成 | AI 可建议确认完成，最终必须由用户确认 |
| 扫描基线 | 用于识别后续变化的有效参照；首次运行建立基线 |
| 完整报告与简报 | 完整报告保存在本地；飞书发送适合快速阅读的摘要 |

学习笔记存在不证明已经掌握；代码修改或提交不证明测试通过或已经上线。文档中的“测试通过”属于文档记录，实际测试输出属于另一类证据，报告不能混淆两者。

不提供生产力评分，不按文件数量推算完成百分比。有明确检查项时，可以描述哪些已有证据、哪些仍待确认。

## 三、首版范围

### 3.1 必须具备的能力

| 能力 | 首版范围 |
|---|---|
| 周目标管理 | 想法输入、AI 起草、用户确认、生效版本与完成确认 |
| 证据采集 | 指定目录内允许文件及 Git 变化，首次基线、后续增量比较 |
| 目标复盘 | 关联证据、解释进展、指出距完成的差距与不确定性 |
| 报告输出 | 本地完整报告与飞书简报，采用已确认结构 |
| 建议与反馈 | 以现有目标为主；新增目标建议及纠错由用户确认 |
| 定时与恢复 | 每日定时、手动触发、遗漏合并补跑、避免重叠 |
| 异常与数据管理 | 失败恢复、外发控制、报告和证据保留、受限清理 |

### 3.2 不纳入首版的能力

多人使用、全盘扫描、屏幕及键盘采集、浏览历史和聊天记录采集、会议录音采集、自动执行建议、自动修改工作文件、生产力评分、自动认定目标完成，以及通过飞书回复确认目标或纠正报告。

系统不为验证进展而自动运行项目或执行测试，只分析已有证据。

## 四、周目标与反馈管理

### 4.1 起草与确认

用户先提供想法，由 AI 起草周目标，再由用户通过本地 Markdown 确认。草稿与已确认目标必须有明确状态，只有已确认的版本用于正式目标复盘。

目标应表达期望结果和完成标准；关联目录或项目只是寻找证据的线索，不能代替完成判断。具体 Markdown 字段和格式在技术方案中明确。

AI 可以根据证据提出“建议确认完成”，但不得自行将目标标为完成。下一步建议以现有周目标为主，也允许提出新增目标建议；新增目标必须经用户确认后生效。

### 4.2 周期及版本

- 一周按北京时间周一至周日计算。
- 新一周没有已确认目标时，仅生成工作摘要并提醒确认，不自行设定目标。
- 上周未完成目标可以建议延续，但不得自动转为本周目标。
- 周中调整目标，从用户确认生效时起使用新版本，保留调整时间和原因。
- 跨周补跑按对应周的已确认目标分析，不用新目标评价旧工作；证据不足以确定归属时间时，应明确不确定性。
- 历史报告保留当时的判断依据，不悄悄按新目标改写；用户明确要求时再回顾重评。

### 4.3 反馈与修订

用户通过本地 Markdown 补充未被采集的工作、纠正报告或确认判断。反馈在下一次复盘时读取，需要立即获得修正结果时可手动触发。

旧报告保留，修订版说明修改内容。修订报告默认只保存本地，重新发送飞书须由用户明确触发。后续复盘采用已确认的纠正，不继续沿用已被否定的结论。

飞书首版仅承担通知，不把群内回复视为已被系统接收或确认。

## 五、证据范围与采集规则

### 5.1 授权目录

唯一已确认的扫描根目录为：

```text
/Volumes/Work-Data/专业/11-AI/06-AI工程化实战
```

只读取该范围内允许的材料，不扫描整块磁盘。目录内同时存在学习资料和项目，应区分笔记变化、代码实现、验证记录及复制参考资料等不同性质的证据。

### 5.2 允许的证据

- Markdown、纯文本及其内容变化。
- 指定范围内 Git 仓库的提交、已暂存和未暂存差异，以及允许的未跟踪文件。
- 选定的测试报告、验收记录和用户主动补充说明。

允许读取正文及代码差异，不只读取文件名。密钥配置、依赖目录、构建产物、缓存和二进制文件默认排除；需要使用的测试报告通过指定路径单独纳入。

### 5.3 增量与采集状态

首次扫描只建立基线并说明结果，不将既有内容全部计为当天工作。后续比较上次成功采集的有效基线与本次变化，注明实际覆盖时间；跨多天变化不能全部归到当天。

根目录不可访问时不更新基线。部分文件失败时保留待补采状态，可读部分的成功不能掩盖缺失范围。已采集但未分析成功的证据需要保留，以便恢复处理。

相同变化不重复计为新增进展。构建、同步、自动保存或 AI 批量生成内容不能直接等同于用户有效进展。

### 5.4 排除助手自身输出

助手的报告及自身输出数据目录不作为普通工作证据，避免把自动生成的报告再次当成用户工作成果。周目标和反馈文件作为专门输入读取，不计为普通产物进展。

## 六、数据使用与外发边界

| 环节 | 已确认规则 |
|---|---|
| 本地读取 | 仅限授权范围内允许的材料 |
| 云端模型输入 | 允许发送已确认周目标、相关文件必要片段、代码差异和验证摘要；先过滤凭证及敏感信息，不上传整个目录 |
| 飞书输出 | 仅向用户自己的群发送进展、简短证据摘要、相对路径、待确认事项及建议；默认不发送完整代码、原始日志或大段文档 |
| 本地报告 | 保存完整复盘及证据引用，供用户回查 |

本地采集不等于数据完全不离机，模型输入和飞书输出分别受控。扫描到的文件属于分析材料，不能被当作授权系统执行动作的指令。

聊天中作出的确认，只有被保存到允许读取的记录后，才能成为助手可用的证据；不能假设助手天然知道其他对话的内容。

## 七、报告结构与表达规则

| 部分 | 内容 | 规则 |
|---|---|---|
| 复盘范围 | 日期、实际采集区间、采集完整性 | 跨多天或部分失败时说明 |
| 本周目标进展 | 逐个目标描述今日推进、证据和未满足标准 | 未发现证据不等于没做事 |
| 其他工作摘要 | 未关联本周目标的有意义变化 | 不直接认定为偏离目标，允许补充关联 |
| 下一步建议 | 最多三条，按优先级排列 | 写明行动及理由，不自动调整目标 |
| 待用户确认 | 完成建议、证据疑点、遗漏工作 | 无待确认事项时省略 |

每个目标的核心表达为：目标、今日推进、依据、距离完成还差什么。事实与推断应能区分，证据引用应可回查。

飞书简报一般约 500～800 字，证据过多时保留关键项，完整内容留在本地；该长度是可读性目标，不要求异常简报或无变化报告凑字数。

## 八、定时执行与关键流程

### 8.1 正常流程

每天北京时间 **21:30** 执行，包含周末，时间可配置。流程为：

确认可用目标 → 采集变化 → 分析目标进展 → 保存本地报告 → 发送飞书简报。

同时支持手动生成一次。前一次尚未结束时，不同时启动第二次，记录本次未执行原因。

### 8.2 遗漏补跑

电脑休眠或程序未运行造成遗漏时，恢复运行后合并补跑一次，覆盖遗漏区间，不补发多份日报。报告必须说明实际覆盖时间。

电脑关机时无法自行执行或发送故障通知，只能恢复后检查遗漏。跨周分析按第四章处理。

### 8.3 分阶段状态

分别记录采集成功、分析成功、本地保存成功和飞书发送成功。前一阶段成功不代表全部完成；飞书失败时保留已生成报告，重试发送不重新采集或分析。

## 九、异常处理要求

| 异常 | 必须采取的行为 |
|---|---|
| Work-Data 未挂载或根目录不可访问 | 标记采集失败，不更新基线，恢复后补采 |
| 部分文件无法读取 | 可生成部分报告，说明缺失范围，失败文件保留待补采状态 |
| 未发现变化 | 正常生成简报，说明未发现新的产物变化，不评价用户没有推进 |
| 周目标缺失或未确认 | 仅生成工作摘要并提示确认，不自行设定目标或评价目标进展 |
| 模型超时或暂不可用 | 最多重试 2 次；仍失败则保留已采集证据等待后续处理，不编造结果 |
| 鉴权失败或配置错误 | 直接提示处理，不反复尝试 |
| 本地报告保存失败 | 不标记完成，停止飞书发送，保留恢复所需状态 |
| 飞书明确返回发送失败 | 最多重试 2 次，只重发通知，不重新分析 |
| 飞书请求超时、是否送达不确定 | 标记送达待确认，不立即自动重发 |
| 飞书不可用 | 异常先保留在本地，不声称故障通知已送达 |

“最多重试 2 次”指初次尝试失败后的追加尝试次数。失败文件和待分析证据不得因其他阶段成功而丢失。具体重试间隔、状态持久化和恢复机制由技术方案明确。

## 十、数据保留与清理

| 数据类型 | 保留规则 |
|---|---|
| 本地完整报告及修订版 | 默认 90 天，可配置；旧版在保留期内保留 |
| 周目标、确认及反馈 | 持续保留，由用户手动归档或删除 |
| 临时片段及差异证据 | 默认 7 天；尚未处理成功的不提前清理 |
| 当前有效扫描基线 | 持续保留，不按报告期限清理 |
| 飞书历史消息 | 首版不自动删除，遵循群内实际保留情况 |

自动清理仅作用于助手自己的数据目录，不能删除扫描源目录中的原始工作文件。具体数据目录及期限计算方式在技术方案中明确。

报告保留路径与摘要，但不承诺永久还原原始文件。文件后续修改、删除或临时证据过期后，引用可能无法完整回放；需要长期留存的证据由用户另行保存。本地删除不代表模型服务端或飞书中的数据同步删除。

## 十一、功能验收标准

下列 A01～A12 已由用户确认，全部属于未来实施后的验收要求，当前均未执行。

| 编号 | 验证场景 | 通过标准 |
|---|---|---|
| A01 | AI 起草或建议新增目标 | 未经用户确认不生效，AI 不自行标记完成；跨周延续及周中版本按规则处理 |
| A02 | 首次扫描 | 建立基线，不把历史文件算作当天工作；助手自身输出不计入工作产物 |
| A03 | 修改文档、代码及新增未跟踪文件 | 识别允许范围内变化，证据可回查，相同变化不重复计入新增进展 |
| A04 | 测试用凭证、缓存和构建文件 | 禁止内容不进入模型请求或飞书报告；使用假凭证验证 |
| A05 | 文档声称完成但缺验收证据 | 说明来源及不足，不直接认定验收通过 |
| A06 | 无变化、目标缺失或目标外工作 | 如实表达，不推断没工作、不自动创建目标 |
| A07 | 正常定时与手动执行 | 产生本地报告和飞书简报，结构正确，实际群内收到；首次基线和修订发送遵循特别规则 |
| A08 | 错过执行或连续触发 | 恢复后合并补跑一次，时间范围清晰，不重叠执行 |
| A09 | 根目录或部分文件不可读 | 不误报完整采集，恢复后能补采遗漏内容 |
| A10 | 模型或本地保存失败 | 不丢待处理证据、不编造报告，保存失败不发送 |
| A11 | 飞书明确失败或结果不确定 | 明确失败按上限重试，不确定时待确认且不自动重发 |
| A12 | 用户补充或纠正判断 | 后续采用已确认纠正，旧报告保留，修订内容明确，修订版默认只保存本地 |

数据保留规则还需核验：报告按默认 90 天及配置处理；临时证据按 7 天处理但不提前删除未处理成功的数据；目标、反馈、有效基线及原始工作文件不受自动过期清理影响。期限边界可使用可控时间验证，无需等待实际经过 90 天。

## 十二、连续 7 天个人试用

功能验收之外，连续试用 7 天，每天记录：

- 是否遗漏重要工作或误判目标进展。
- 阅读、补充及纠错用了多少时间。
- 建议是否有用，未采纳是否因为不准确、优先级不合适或已有安排。

试用结束由用户判断是否值得继续使用，不把连续发送成功等同于产品价值已验证。本轮未规定采纳率、准确率或节省时间的量化门槛，不自行补充承诺。

## 十三、技术方案需要落实的事项

以下是已确认行为的设计细节，不作为新增产品范围：

1. 目标草稿、确认版本、完成确认和反馈 Markdown 的格式及读取规则。
2. 授权目录内文件过滤、Git 变化归集、基线及重复识别方式。
3. 跨天、跨周证据归属与无法确定时间的表达。
4. 未处理成功证据的持久保存、恢复及清理条件。
5. 防重叠、遗漏补跑、重试间隔及发送结果不确定时的人工处理方式。
6. 助手数据目录、报告修订命名、保留期限计算和受限清理机制。
7. 模型输入过滤、飞书输出过滤及对应验证方式。
8. 所选 OryxOS 版本可复用能力与需要新增的适配；不把规划能力当成已实现能力。

若技术设计发现必须改变已确认的用户行为、权限或范围，应回到需求确认，不以实现细节为由自行扩展。
